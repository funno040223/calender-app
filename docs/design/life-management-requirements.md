# 生活管理アプリ 要件定義

2026-11-20。基準は main の `c305fbc`。この文書は目的・合意・検討経緯を記録する。初版は 2026-11-21 に `c9cc51e` で実装した（料理 `/meals`・運動 `/exercise`、`src/lib/life/`・`src/components/life/`）。挙動の正はコードとテストで、下の個別仕様は実装前に決めた内容。

## 1. 何を実現したいか

仕事や学習の予定と、食事・運動・睡眠に使う時間が競合する一日を無理なく組み立てる。外出が延びたら夕食を簡単なものに変え、空いた時間を使いたければ予定を組み直せる。日常の価値は、入力したデータ量より「次にどうするかを、迷わず決められること」にある。

**ユーザーが示した要件**　主な利用端末はスマホで、日々のタスク管理とスケジュール調整を中心に、カレンダーとしても使う。料理と運動に専用画面を設ける。今どこにいて何ができるかが伝わる見た目・操作と、日々の入力負担の小ささを重視する。比較や判断に必要な情報は一緒に見せる。既存の機能・記録を引き継ぐ。今日の依頼範囲は要件定義。画面構成や実装手段は変更できる。

**設計案**　一つのアプリに、用途別の画面を持たせる。共有するのは生活行動の予定時刻・長さ・実施状態・詳細へのリンク。料理の材料や運動のセット数は各画面で扱う。

| 選択肢 | 日常の利点 | この用途での代償 |
|---|---|---|
| 別アプリにする | 各アプリの目的は明快 | 寝坊・外出・運動の延期が複数の予定表にまたがる。実績の取り違えや二重入力を解く仕組みが要る |
| 既存の「今日」にカードを足す | 少ない改修で呼び出せる | タスクを確かめたいときにも、在庫や運動レビューを通り過ぎる。現行画面にも条件付きカードが多数ある |
| **一つのアプリで画面を分ける（採用）** | 一日の空き時間は共有でき、台所・運動中には目的の画面へ直行できる | 専用画面に入る手数が増えるので、今日の枠から直接対象を開けるようにする |

料理・運動を単独で開く利用が多くなった場合は、まずショートカットや直リンクを試す。独立配布や異なる利用者などの要件が生じた段階でアプリ分割を再検討する。

### 全体の改修方針（2026-11-20 基本方針に合意）

スマホで一日の時間を配分する機能を土台に、料理・運動を同じアプリに組み込む。目指す成果は、体型を整え、希望に応じて変化を振り返れること、外出後も活動を続ける余力があること、日中の眠気による中断が減ること。食事と運動を改善しやすくするのが主な手段で、睡眠・休息・予定の組み方も検討対象にする。生活管理アプリへの移行に合わせ、ホーム・主ナビ・運動画面を含めて構成を再設計する。既存の予定配置・記録・連携は活かし、簡易的な運動UIは刷新する。

| 領域 | 方針案と変更の大きさ |
|---|---|
| 今日・週・月、タスク、生活リズム | 流用が中心。進捗確認、時間の再配分、月の締切、起床・就寝・休息の記録を使う。生活リズムは既存の導線で扱い、記録を追加する必要が出た場合に拡張する。 |
| 料理 | 新設が中心。定番と自分で追加したレシピ、買い物と手持ち材料、その時点で作れる候補、食べた記録を扱う。既存の食事枠と家／外の選択を入口にする。食事予定のない買い物中にも単独で開ける。 |
| 運動 | 習慣の予定・短縮達成・見直しを流用し、メニューと種目別の実績を新設する。延期後の間隔や短縮後の空き時間は既存の配置処理に反映する。ジムは初版対象外。種目別の自動提案は必須とせず、まず手動調整で使えるようにする。 |
| 保存・同期と画面間の移動 | 複数機能にまたがる主な改修。予定を動かしても実績を保持し、実食や運動の訂正を在庫・集計・報酬に一度だけ反映する。「今日」と予定表は対象の食事・運動へ進めるようにする。主ナビも生活管理の使い方から組み直す。 |

例として、外出が延びて夕食を自炊から外食に変えたとき、時間の組み直しは今の予定管理が担う。買い物の残りと実食は料理画面が扱い、すでに購入した材料は次の食事に使える。この分担なら、料理・運動が増えても普段のタスク確認の手順を保てる。

## 2. 使う場面と画面の責務

以下は画面の役割を整理した案。当日の行動は「今日」、直近の調整はカレンダーの週表示、先の締切の確認は月表示で扱う。

| 入口（仮称） | 開く理由／主操作 | 最初に見せる内容 |
|---|---|---|
| 今日 | アプリを数秒開いて、次の行動を決める | 現在・次の予定、今必要な操作一つ、当日の流れ。朝・帰宅・就寝の操作や、解決が必要な競合を状況に応じて出す |
| 予定 | 予定を調整する、タスクを追加・分割・見直す | 現行のカレンダーとタスクを同じ入口の「カレンダー／タスク」切替で開く。生活枠は予定表上では時刻・短い名前・所要時間まで |
| 生活 | 生活上の行動を選ぶ、あとから実績を補う | 料理・運動を独立タブにする最新案では、生活の専用トップは保留。睡眠・ルーティン・その他の習慣と既存の記録への導線を保つ。トップに専用画面の中身を複製しない |
| 料理 | 買い物を決める、今の一食を選ぶ | 既定は「次の食事」。同じ画面から定番一覧と買い物リストへ。時間が過ぎた食事も後から記録可能 |
| 運動 | その場で始める、短縮・変更する、負荷を決める | 今日の種目・時間と「通常／5分だけ／見送る」。回数・負荷・過去の実績は必要なときに開く |
| 記録・設定 | 振り返る、動作を調整する | 全体の記録は既存の集計を維持。設定は共通入口に残し、各画面から関連項目へ直行できる |

スマホのホームは短時間の確認・選択に使い、左右にページを送れる構成を検討する。初期案は「いま」（現在・次の予定と朝食などの選択）と「一日の予定」（当日の時間割）。上部に両方の名前と選択状態を出し、タップでも切り替えられる。下部タブは時間をかけて操作する場所への固定入口とする。最新の構成案は「ホーム／予定／料理／運動／記録」。予定タブの入口はカレンダーとする。タスクへの直リンクは従来どおりタスクを開く。予定内のカレンダー・タスクは表示された見出しをタップして切り替える。カレンダーの横スワイプは日付送りに使う。記録は全体をまとめ、項目別に詳細を開く。設定は各タブ最上位の右上から専用画面へ進む。この配置を初版の既定とする。PCは同じ分類をサイドバーに出し、料理・運動へ直接移動できる。今日の食事・運動枠からは1操作で該当の詳細へ移動。買い物中は当日の食事枠がなくても料理を開ける。カレンダー・タスクの現行URL、ブラウザの戻る、通知やホーム画面の直リンクを引き継ぐ。

| 今日のタイムライン、今できる作業、進捗・締切不足、予定の組み直し・取り消し | 「今日」に今必要な操作、「予定」に全体調整。いつ・なぜ再配置されたかと取り消しに到達できる |
| カレンダー、固定予定、タスク、クイック追加、時間割、場所・移動、タグ、避けたい時間 | 「予定」。固定した枠、締切と休憩、今の自動配置・編集を維持 |
| 起床・就寝、朝の手順、帰宅時の体力、立て直し、習慣・楽しみ・連絡・喫煙の記録 | 現在必要な操作は「今日」、随時の実行・修正は「生活」、履歴は「記録」。時刻に依存した挙動も確認する |

## 4. 料理で必要な機能

1. **買い物から始める。** まとめ買いでは、あらかじめ作った複数の定番リストから今回使うものを選ぶ。帰りがけの買い足しでは、その日作りたい料理に足りない材料や、普段のストックで切れた品だけを買える。食べる曜日は固定せず当日に選ぶ。重複する材料を合算し、手元にあるものを差し引く。購入と実食は別々に記録。初期案は「ある／足りない／不明」を許し、在庫量を毎回量らなくても使える。単位が異なる材料を根拠なく足さない。
2. **食事枠ごとに切り替える。** 朝はトースト・バナナとヨーグルト・おにぎりと卵などの簡単な定番。昼夜は「さっと済ませる／自炊したい／外食」を独立して選ぶ。外出予定だけで外食を確定しない。疲れて帰宅した日は基本的に調理しない。夕食を決める時点で自宅候補の料理名と所要時間を見せ、「外食」「宅配」を並列に出す。外食・宅配は方針だけ選べば済み、店・料理の選択や入力は求めない。
3. **定番から選び、作りたい料理を追加できる。** 初期のレシピを用意し、利用者が追加したレシピも食事の候補として選べる。初期収録はコンテンツ仕様に従い、さっと済ませたい日と自炊したい日の両方に候補を用意する。名前だけで保存でき、材料と分量を追加すると買い物・消費量に使える。手順・時間・参考価格は任意。準備可能な上位3品を先に出し、全候補も開ける。材料・準備時間・使い切りを考慮し、直近に食べた料理とは別の候補も提示する。同じ料理をまた選ぶことはできる。栄養は1食の量・概算kcal・たんぱく質・野菜の有無、価格は参考値。表示値の出典や概算・不明を区別する。生成AI、精密なカロリー最適化、外部注文は初版の要件外。
4. **食べたら終わる。** 「食べた／別案／材料切れ」。食事を変更・延期しただけでは在庫を消費しない。実績からの訂正で消費量と集計を戻せる。外食・宅配の食事は自宅在庫を消費しない。入力なしは不明とする。

例：今週は肉うどんと焼きうどんを各1回、自炊できない日のために冷凍弁当を1個。買い物にはうどん2玉が一行で出る。当日夜に外食へ切り替えると、未購入分の必要数を再計算し、すでに買ったうどんは次の候補に残る。

## 5. 運動で必要な機能

**目的と振り返りの案**　歩行は、同じ道・階段の負担や外出後の余力で振り返る。自宅筋トレは、腕立ての台の高さと回数、背中を引く動きなど、種目ごとの変化を比較する。長時間の机作業には、作業の区切りで任意の短い離席や肩まわりの動きを選べる案とし、作業後の負担を振り返る。体型は希望時のみ長い間隔で推移を見る。日中の強い眠気や普段と違う息切れを運動不足と判定しない。本人の生活上の目標は設計の根拠とし、個人の症状はサンプルデータに含めない。

- **始めやすさ。** 自宅を初期候補に、週2回の非連日を選べる。通常版は台腕立て・リュックを引く・椅子から立つ・ヒップブリッジ、短縮版は2種目。歩行は通勤や室内に振替可能。休憩は任意で、見送った休憩を未消化タスクにしない。
- **時間と負荷を区別。** 歩行の実績は分数、筋トレは種目・回数・セット・重量または台の高さ。詳細は任意で前回値を再利用。通常／短縮の完了は1操作。未入力の重量をゼロとして扱わない。
- **段階を選べる。** 導入例は歩行5〜10分×週3、全身運動10〜15分×週2。次に歩行15〜20分と種目ごとに2セット、続けば歩行20〜30分・筋トレ20〜30分へ。週数の経過で自動進級しない。2週間の見直し機能を利用。本人が選んだ種目だけ増量し、既存の時間延長と重複適用しない。
- **将来自動提案を採用する場合の条件。** 例として、通常版で対象種目の全セットが上限に2回連続で達し、余力と翌日の回復が確認できたら、重量・難度・セット数のどれか一つを提案。回復不明なら維持。痛みや普段と異なる息苦しさを記録したときは増量提案を抑え、見送れる。診断・画像による姿勢判定は対象外。
- **ジムは振替。** 将来、週の自宅枠をジムに置き換えられる。所要時間には移動・着替えを含め、運動実績には実働のみを記録。マシン重量と自宅種目の難度を別に扱う。初版は会員・予約管理まで作らない。

### 運動の選び方（設計案）

画面上の短い分類は「有酸素」「筋トレ」「ほぐす」。具体的な予定には「歩く 10分」のように実際の動きを出す。有酸素は日常の持久力をねらい、歩行時間やペースを本人が調整できる。走ることは必須の進級条件にしない。筋トレは基本種目を繰り返して前回と比較し、回数・難度・セット数のどれか一つを手動で変えられる。通常と5分版は使える時間の違い。「ほぐす」は机作業の区切りに使う任意の短時間メニュー。これらを初版の表示名とする。[有酸素運動の強度（CDC）](https://www.cdc.gov/physical-activity-basics/measuring/) ／ [筋力トレーニングの指針（ACSM）](https://acsm.org/resistance-training-guidelines-update-2026/)

### 予定と疲労に合わせた運動の調整

要望は、実行日の予定と本人の疲労に合わせて種目・強度・長さを変えること。現行の空き時間・予定の負荷・締切までの作業見通しを利用する。以下は設計案。通常版・短縮版・延期または見送りを仮に置き、固定予定・休息・締切までの作業への影響を比較する。時間は足りても本人の疲れが強ければ負荷を下げ、疲れが少なくても締切に必要な時間を奪う候補は外す。疲れの未入力は不明として扱う。既存の記録を使い、毎回の体調入力は求めない。

通常枠を変更する場合は「締切が近いため5分」など短い理由をホームで確認でき、本人が変更できる。合意事項として、運動は週の中で優先して確保する。通常枠が難しい日は短縮・週内の別日を比較し、固定予定、休息、締切に必要な作業時間を守れる候補がないときに見送る。忙しい日があるだけで週から消さず、翌週の義務にも積み増さない。本人が選んだ枠は維持し、競合時のみ確認する。運動内容の当日調整と、週をまたいだ筋力の増量提案を別に扱う。

### 運動枠を開いたときの初期メニューと簡易完了

種目ごとに、初めてのうちは動きが分かる短い動画またはアニメーションをその場で見られるようにする。慣れたら図で確認でき、必要なときは動く見本に戻れる。

- 通常版（目安10〜15分）は軽い足踏みから始め、壁腕立て、リュックを引く動き、安定した椅子からの立ち座り、ヒップブリッジを楽な回数で各1セット。間に休み、最後に壁に手をついて左右のふくらはぎを軽く伸ばす。
- 5分版は軽い足踏み、壁腕立て、椅子からの立ち座りの順。2種目は各1セット、初回の表示目安は各5回。最後に左右のふくらはぎを軽く伸ばす。時間・回数は目安で、休憩や中断を選べる。痛みや普段と違う息苦しさがある日は中止できる。
- 実施前に選んだ内容を表示し、終了時は「通常で完了／5分版で完了」でその回を1件保存する。種目別回数・重量・実働分数は詳細入力があった分だけを実績にする。前回値は編集の候補として表示する。
- 2週間レビューでは「似た外出の後、夕食や趣味を楽しむ余力はあったか」など本人が選んだ変化を任意で振り返り、維持・調整を選べるようにする。本人は機能に前向き。初版は2週間ごとの既存レビューで任意の1問を表示する。選択肢は「楽／いつも通り／きつい／今回は飛ばす」。別の目標は「肩の楽さ」「腕立ての変化」から選べる。

種目はノートの自宅プランと[NHSの筋力運動例](https://www.nhs.uk/live-well/exercise/strength-exercises/)・[柔軟運動例](https://www.nhs.uk/live-well/exercise/flexibility-exercises/)を参照。順番・時間配分はアプリの初期案。

## 6. 一緒にするデータ・日常の使いやすさ

| 操作 | 共有する結果 | 専用画面で扱う詳細 |
|---|---|---|
| 昼食を外食に変更 | その食事枠の意向・必要な場合の所要時間変更 | 献立候補、買い物必要量、実食の有無 |
| 夜の運動を短縮／延期 | 枠の長さ・配置・その回の実施状態。空いた時間を既存ルールで再計算 | 種目、セット、重量、回復 |
| 過去の実績を訂正 | 同じ実績IDで集計・報酬・関連する提案を更新 | 在庫消費の差分、種目別進捗 |

予定・実績・繰り返し習慣の設定に別の識別子を使い、再配置で過去の実績を消さない。同じ操作の再送や二重タップでは1回分だけ保存する。詳細を閉じても簡易完了は有効。既存のローカル保存・同期・取り消し・オフライン時の案内を尊重し、競合時に在庫や報酬が二重反映されないことを検証する。

アプリ全体で、行き先・操作・状態の違いを把握しやすい箇所にアイコンを使う。既存の線画に線幅・丸み・色をそろえ、絵文字や装飾目的の多用は避ける。意味が曖昧なものには短いラベルを添える。

初回に全機能の設定を求めない。料理を初めて開いたときに定番を、運動を初めて開いたときに通常版を選べる。PCとスマホで名称・記録の意味をそろえる。主操作を一本化し、場所・状態を色だけで伝えない。キーボードとタッチの両方で操作でき、詳細画面への往復後も日付と選択を保持する。

性能は実装前に端末・回線条件を固定して「今日」「予定」の初回転送量・表示時間を測定する。受入時には同じ条件で比較し、料理カタログ・運動履歴を開くまで専用データ取得や重いUIの初期化が発生しないことを確認する。新しい通知は明示的に有効化したものだけ。個人の食事・運動実績や認証情報をリポジトリ、公開カレンダーの件名、既定の通知本文に埋め込まない。

## 7. 改修の順序と受け入れ条件

| 段階 | 成果 | 終了の判断 |
|---|---|---|
| 0　全体設計 | スマホのカレンダーを中心に、料理・運動、既存機能、記録のつながりを設計する | 初版の範囲と主要操作、データの扱い、受け入れ条件がまとまった段階で、全体を実装に移す |
| 1　画面の整理 | ホーム・予定・料理・運動・記録と設定に既存の機能を割り当てる | 第3節の全機能と現行URLに移動できる。旧データで予定・習慣の結果が変わらない |
| 2　生活の専用画面 | 定番と追加レシピ・買い物・実食、運動の通常／短縮・回数記録を実装 | 今日から1操作で詳細へ。料理や運動を使わない日も予定操作の手数を増やさない |
| 3　使ってから改善 | 種目別の進級、振替、食材の使い切り、必要なら外部サービスとの連携 | 実際に選ぶ手間・記録負担が減ったものを残す |

最低限の操作確認は以下の通り。スケジューラの既存テストに加え、変更した導線をPC・スマホで確認する。

1. 外部予定が延長されても固定予定が動かず、生活枠と作業枠で時間を二重に使わない。
2. カレンダーまたは今日の夕食枠から同じ詳細へ行ける。外食に切り替え、翌日に実食を追記しても在庫集計が正しい。
3. 食事の枠が過去になった後も、料理画面から実績を修正できる。候補が0件なら不足材料または別モードを案内する。
4. 運動5分版の完了後に予定を再編成し、さらにPCで再表示しても報酬・運動回数は1回。詳細なしの完了で増量は提案されない。
5. 水曜日に全身筋トレを延期・実施した場合、木曜日に同じ通常版を自動配置しない。
6. 新機能を使わない既存ユーザーが通知から対象の予定を開き、タスク追加・取り消し・外部連携・睡眠記録を従来どおり使える。
7. スマホで週を計画し、当日の食事を選び、同じ記録を後から訂正できる。専用画面から戻ると元の予定・日付に戻る。
8. スマホで作りたい料理を追加し、後からそのレシピを選んで食事の予定に使える。

## 8. 聞き取りの記録（2026-11-20）

### 今回確認した方針

- **主な使い方**　スマホで日々のタスクを管理し、予定を調整する。今日の動きと直近約1週間をよく見て、月単位ではタスクの締切を確認する。
- **操作**　必要最小限にする。入口の深さを尋ねる質問は意図が伝わらなかった。次回は「予定表で夕食を押すとその食事が開く」など、利用場面と操作を示して検討する。初版は下のタブを「ホーム・予定・料理・運動・記録」の5つにし、設定は各画面の右上から開く。
- **料理**　基本のレシピを用意し、作りたい料理ができたら自分で追加できるようにする。在庫の扱いは料理・レシピ次第。初期食材の管理単位はコンテンツ仕様にまとめた。
- **進め方**　カレンダー・料理・運動を含む全体を設計し終えてから、まとめて実装に移る。今回の成果は要件書の更新。次のチャットでも、決まった内容と残った論点をここに追記する。

### 既存の設計から引き継ぐこと

| 見る範囲 | 利用目的と既存の動作 |
|---|---|
| 今日 | 次に何をするか決め、作業の進み具合に応じて残りの予定を組み直す。既存の「今日」のタイムラインと進捗確認がこの役割を持つ。 |
| 直近約1週間 | 固定予定と作業枠を見渡し、空き時間と照らして調整する。スマホのカレンダーには3日・週表示があり、タスク画面では今週・来週の作業時間と空き時間を見られる。 |
| 1か月 | タスクの締切日を先まで見渡す。既存の月表示で締切を表示する。作業枠の自動配置は従来どおり締切の2週間前からとする。 |

「1日」は今日の動きを把握したいという利用目的。カレンダーに新しい1日表示を設ける要件は出ていない。料理・運動を加えるときも、固定予定を尊重し、実際の進捗に合わせて残りの時間を組み直すという設計を引き継ぐ。既存仕様と重なる論点は資料と現行実装を参照し、新機能との接点を中心に検討する。

参照先は[既存の設計意図と配置ルール](2026-09-30-recovery-and-progress.md)、[今日の画面](../../src/components/today/TodayScreen.tsx)、[カレンダーの表示切替](../../src/components/calendar/CalendarApp.tsx)、[月の締切表示](../../src/components/calendar/CalendarView.tsx)、[タスクの週別見通し](../../src/components/tasks/TasksScreen.tsx)。

### 朝の使い方と追加機能の候補

当日の行動とカレンダーを重視し、予定から料理・運動を直接開ける。ホームと主ナビの配置は生活管理向けに再設計する。朝食は起床後の画面で扱い、無理なく収まる定番3件程度を同時に表示する。料理名を1回押すと選択と実食記録が完了する。「食べない」を1回押した日は欠食として記録し、在庫を消費しない。何も押さなければ未記録。後から選び直した場合も、その食事の在庫と集計を訂正できる。

以下は検討経緯。初版に含めるのは既存の2週間レビューへの任意の振り返り。

- 日中に眠気で予定を中断したとき、既存の「休む」「寝る」に任意の理由を付ける。週の記録で、中断した日数と、開始・終了が分かる場合の時間を振り返る。
- 翌朝早い予定がある日は、既存の睡眠予定と夜の作業枠を使い、「今日は何時に作業を切り上げるか」を夜の画面で確認できるようにする。
- 既存の2週間ごとの振り返りに、外出後に余力があったかなど、本人が見たい変化を一つ選んで残せるようにする。体重や腹囲を選ぶ場合も入力は任意とする。

**ノートとの照合・本人の反応**　生活上の変化を振り返る案には関心あり。眠気による中断の記録と夜の切り上げ時刻の表示は、役立つ場面が明確になるまで保留。この2案は初版から外す。日々の成果を把握したいという希望と、新しい入力欄や通知が必要かは別々に判断する。

**設計への反映案**　料理は「買った材料から次の一食を選ぶ」までに加え、余った材料や手間のかかった料理を次回の買い物で見直せるようにする。運動は簡易完了と種目別の負荷調整を引き継ぎ、既存の見直し時に日常の余力も参考にして、本人が続け方を選べるようにする。新しい記録は、本人が次に何を変えるかの判断に使えるものを優先する。

**食事と費用についての補足**　疲れた日の夕食は外食や宅配で済ませる場面を想定する。費用は、分かる場合に候補の一食あたりの参考価格を見られる程度を案とする。「このくらいなら使ってよい」という目安の設定はアイデア段階。日々の支出入力や月の予算・残高を扱う家計管理は今回の実装範囲から外す方向。

**買い物と作り置き**　先に食数を決め、当日に予定や気分に合わせて選ぶ方針を確認。用意しても在宅・外出を問わず食べずに残ることがあり、その日の気分や同じ料理が続くことも理由として考えられる。作り置きの管理は初版では見送る。買い物で用意した材料を複数の料理に使えるようにし、当日は外食・宅配も含めて選べる。

**買い物リストと在庫**　まとめ買い用には複数の定番リストを作り、繰り返し使う。買い足しはその都度、作りたい料理の材料不足やストック切れに応じて行う。定番リストは普段買う品と量の目安。今回買う量、実際に購入した量、家にある残量は区別する。購入後に「リストどおり買った」で今回の品を一括で在庫に反映する。買わなかった品は今回分だけ外し、元の定番リストに残す。1品だけの買い足しは、その品の購入を確定して完了する。

在庫の扱いは、量（個数やあと何回使えるか）と期限（表示された消費期限・賞味期限）の二つの軸で考える。期限は任意とし、空欄のまままとめ買いを一括確定できる。以下は入力負担を抑えるための案。

| 食材の例 | 購入・使用時の扱いの案 |
|---|---|
| 調味料 | 普段は「ある」で候補に使い、「残り少ない／切れた」で次回の買い物に戻す。毎食の使用量入力は省く。 |
| 卵・牛乳 | 卵なら個数、牛乳ならおおよその使用回数など、扱いやすい単位を使う。分かる場合は購入分の期限も持てる。 |
| 少量ずつ買う野菜など | 今回使う分を買い足し、使い切ったら在庫から外す。期限の表示がない場合は日付を推定せず、早めに使いたい候補として扱える。 |

購入・消費ともに基本操作は合意済み。自炊の「食べた」で、数量管理する食材はレシピの分量を既定値として在庫から引く。本人がその食事の材料別消費量を変更できる（例：卵を2個に増やす、使わなければ0個）。後日の訂正は差分だけ在庫に反映し、元のレシピの分量は保持する。

設計判断の根拠、代替技術、評価シナリオは[iOSの画面構成と予定最適化の調査](../research/ios-navigation-and-adaptive-scheduling.md)を参照。
