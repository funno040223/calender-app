# 生活データの保存・同期契約

2026-11-20。料理の購入・実食・欠食、運動の実施と訂正を、オフライン・複数端末・旧版との併用でも二重計上や消失なく扱うための実装前仕様。既存コードの挙動を確認したうえで、生活記録の追加に必要な契約を定める。既存の状態保存を全面移行するのではなく、新しい生活記録に明示的なイベントIDと版を加える。

## 現行保存・同期の確認

- [MockData](../../src/lib/mock/model.ts) は `version: 2` のユーザー状態で、習慣実績 `habitLogs`、家で食べる意向 `mealsAtHome`、購入物の支出 `rewardSpends` などを含む。実績記録の一部は日付・習慣IDの辞書、他はID付き配列で保存される。
- [state.ts](../../src/lib/mock/state.ts) は `DATA_KEYS` を使って保存対象を列挙し、`fromStoredV2` が欠損値を補い、`migrations` の識別子で初期値変更を一度だけ適用する。キーを追加する場合は `DATA_KEYS` と `MockData` の両方を更新しないと型検査で検出する。旧形式v1は `migrateV1` でv2に移す。
- [merge.ts](../../src/lib/mock/merge.ts) は各キーの安定指紋と前回同期時の基準値で変更を判断する。片側だけの変更はその側を採用し、両側変更は配列・辞書を union する。同じIDの配列要素はサーバー側要素を採用する。削除の墓標はなく、一般の同一キー競合は意図した削除を復活させる場合がある。睡眠のみ夜ごと・寝起き別の専用マージがある。
- [store.ts](../../src/lib/mock/store.ts) は `localStorage` を即時表示用・オフライン用の控え、Supabase `app_state` を同期先とする。保存を800ms遅延し、初回ロードを最大6秒待つ。同期後はサーバー時刻・端末編集時刻・キー指紋を保持し、復帰時やオンライン化時に再取得する。失敗した保存は `dirty` のまま再同期対象となる。
- [remote.ts](../../src/lib/sync/remote.ts) はユーザーごとに1行の `app_state.data` を `upsert` する。現行クライアントは `version: 2` を送る。SQLの主キーはユーザーID、RLSは本人の行への読書きに限定する。JSON全体の `upsert` には期待revision条件がなく、アプリの指紋マージに到達する前の競合や再送の冪等性はDB側では保証されない。

現行の一般的な「後から保存された方」マージだけでは、在庫の差分、同じ食事の競合、削除・訂正の意味を区別できない。以下の契約を生活データに適用する。

## 保存モデルと版

### 1. 正本は追記型の生活イベント

生活実績・在庫変動は上書き可能な集計値ではなく、追記型イベントとして保存する。各イベントは次の共通項目を持つ。

| 項目 | 契約 |
|---|---|
| `id` | UUID。端末がオフライン中に生成し、再送しても同じIDを使う。1操作の一意キー |
| `schemaVersion` | レコード形式版。現行は初版で `1`。未対応の版は無視して上書きせず、同期を保留して更新を案内 |
| `kind` | `purchase` / `meal` / `exercise` / `correction` / `stocktake` のいずれか |
| `occurredAt` | 購入・食事・運動が実際に起きた時刻。未確定なら未確定のまま |
| `recordedAt` | 端末で記録した時刻。競合の説明・並び順に使う。端末時計だけで削除・勝者を決めない |
| `deviceId` | 端末識別子。診断・競合表示用。ユーザー間の識別には使わない |
| `supersedes` | 任意。訂正対象となるイベントID。訂正は対象を消去せず、この参照で新しい内容を示す |
| `payload` | 種別に応じた値。数・単位・レシピスナップショットなどを含む |

イベントは不変。訂正、取り消し、削除も新しい `correction` イベントで表し、元イベントを消さない。再投影時はイベントIDで重複排除し、対象ごとの訂正関係を解決してから集計する。集計値・画面キャッシュは再生成できる派生値で、正本として同期マージしない。

### 2. 生活操作のデータ形

- **購入**：購入イベントID、食材ID、数量、単位、実際に購入した量、期限（任意）、記録時点の食材名を保存。「買った」はリストや在庫予定を一括確定する一操作から、食材ごとに安定したIDでイベントを生成する。購入予定・チェックだけでは在庫を増やさない。
- **実食**：食事枠ID（日付＋朝昼夜等の固定キー）、状態 `eaten_home` / `eaten_out`、選択レシピIDと名称・分量のスナップショット、実食時刻を保存。自宅食では材料別の消費量を確定し、外食・宅配は自宅在庫を消費しない。
- **欠食**：同じ食事枠IDに `skipped` を保存する。実食とは排他的な最終状態で、在庫消費は0。操作なしは `unknown`（未記録）であり、欠食と解釈しない。
- **運動**：予定IDとは別の実績ID、運動日、実施版 `normal` / `short`、種目別の任意実績、完了時刻を保存。予定の作成・延期・短縮提案だけでは実績イベントを生成しない。1回の完了操作でIDを一つだけ発行する。
- **訂正**：元のイベントIDを参照し、訂正後の状態・数量・理由（任意）を保存する。材料数量の訂正は訂正後の総消費量を記録し、差分だけを在庫投影に反映する。実食を欠食に直す場合は、元の消費を戻す訂正を同一操作で保存する。

### 3. 在庫・集計の原子性

イベント正本の追加とその同期用revision更新は一つのDBトランザクションで確定する。在庫残量、食材別使用量、食事・運動回数、報酬は同じイベント集合を一貫した順序で再投影し、独立した加算APIを作らない。オフライン時は端末にイベントを永続キューとして残し、イベント追加後に画面を更新する。同期成功確認前にキューを消さない。

同期APIは `event.id` に一意制約を持ち、同じID・同じ内容の再送は成功扱いのno-op。同じIDで異なる内容が来たら拒否して競合を提示する。イベント挿入後に返すサーバーrevisionを端末が保存する。イベント群が一部だけ確定する状態を避けるため、購入一括確定と実食訂正は複数イベントを一つの要求・トランザクションで保存する。

## 競合・再送の規則

| 競合 | 解決規則 |
|---|---|
| 別端末で別の食事枠を記録 | 両方を保持。日付・枠IDが異なるため集計も独立 |
| 同じ食事枠を片端末で実食、別端末で欠食 | 自動で片方を捨てない。両イベントと発生時刻を保ち、枠を「要確認」にする。本人が選んだ状態を訂正イベントとして追記 |
| 同じ食事を両端末で別レシピとして実食 | 枠を要確認にし、在庫消費は確定状態が選ばれるまで二重適用しない。選択後、敗れた記録は履歴に残すが有効消費から外す |
| 同じ購入操作を再送 | UUIDの一意性で一回だけ計上 |
| 別端末で同じ食材を別々に購入 | 別IDなので両方計上。数量は購入イベントごとに足す |
| 同じ在庫残量を両端末で編集 | 残量値への加算競合にせず、実食・購入イベントから再計算。手動棚卸しは `stocktake` 訂正イベントとして数量・基準時点を保存し、同時編集は要確認 |
| 実食・運動の訂正を二端末で別々に行う | 両訂正を保持。共通の元イベントを複数訂正が指す場合、時刻の新しい方を黙って採用せず要確認にする |
| 旧版端末が新しい生活イベントを知らない | 旧版の app_state 更新は従来どおり受理。別表の生活データは影響を受けない |
| 通信切断後に保存を再送 | 操作IDが同じならno-op。別IDの重複操作は区別不能なので、UIは再試行時に新IDを発行せず、前の要求状態を復元して送る |

時刻の大小だけで事実の勝者を決めない。競合は履歴を保持し、ユーザーが選択した結果もイベントとして監査可能にする。予定データの一般マージは現行ルールを継続できるが、生活実績・在庫の正本には適用しない。

## 新旧版・legacy migration

1. **状態形式とイベント形式を分ける。** 既存 `MockData.version: 2` は読み取り互換を維持する。新生活データは `app_state` JSONには混ぜず独立表に置き、イベント `schemaVersion` を持つ。イベント同期用のユーザーrevisionを独立に管理する。`MockData.version` と `app_state.version` の現在値2を生活イベント版と誤用しない。
2. **一方向で段階移行する。** 新版は旧v1/v2を読み、既存 `habitLogs` / `mealsAtHome` / `habitSkips` を維持したまま新形式を追加する。migration IDを `migrations` に記録し、同じ端末で再実行しても重複生成しない。DB移行は列追加・新テーブル追加の順で行い、既存行の書換えを一括必須にしない。
3. **過去に推測で実績を作らない。** `mealsAtHome` は「家で食べる意向」、`habitSkips` は「外で食べる選択」、`habitLogs` は習慣完了の粗い印であり、材料・実食内容・購入量・運動種別の証拠ではない。これらから消費量・実食・運動回数を推測して新イベントへ移さない。旧記録は旧履歴として残し、新方式は導入後の操作から記録する。
4. **旧端末との書込み範囲を分ける。** 旧端末は既存 `app_state` だけを更新し、独立した `life_events` 表を読まず書かないため、その全体JSON upsertで新しい生活イベントを消せない。新端末はlegacy状態とイベントを別々に保存する。イベント表への書込みは対応する `schemaVersion` を検証し、未対応版は拒否して更新案内を返す。将来、新フィールドを `app_state` JSONに追加する場合は、書込み形式世代を検査し、未知フィールドを消す全体置換を拒否する。
5. **失敗時は保留する。** 不正な版・未知の必須イベント種別・同一IDの異内容は隔離して表示し、イベントを破棄しない。migration完了・同期成功まではローカル控えとキューを保持する。

## Supabase側の保存・同期案

現在のユーザー単位 `app_state` JSONBとRLSは引き続き設定・既存状態に使う。生活イベントは独立表（例 `life_events`）にし、主キーを `(user_id, event_id)`、行に `schema_version`, `kind`, `payload`, `occurred_at`, `recorded_at`, `device_id`, `supersedes`, `created_at` を置く。同期revisionはユーザー単位の同期行（例 `life_sync_state`）で管理する。RLSで本人の行だけ読み書きできる。payloadの種別別検証と一意性をサーバー側で行う。

書込みはRPC一回で行い、(a) 認証ユーザー検証、(b) `event_id` 重複・異内容検査、(c) 期待revisionとの比較、(d) 全イベント挿入、(e) revisionを一つ進める、(f) 新revisionを返す、を同一トランザクションで処理する。revision不一致は409相当として最新イベント差分を返し、端末がID重複排除と生活固有競合規則で再マージして再送する。クライアント時刻による `updated_at` 上書きを避け、サーバー時刻を使う。JSON全体の無条件upsertだけで生活データを同期しない。

在庫・回数の派生値はイベントから決定的に再構築可能にする。初版でSQL集計を持つ場合も、イベントトランザクション内で更新し、同じイベントの再送で二度変化しない。集計キャッシュが正本と食い違った場合はイベントから再構築し、手入力の在庫訂正履歴は残す。

### 設定・過去実績との接続

- レシピ、買い物リスト定義、食材、運動プランは利用者ごとの生活データとして別領域に保存する。初期カタログは共通の版付きIDで配布。ユーザー編集は本人用の差分。削除は非表示として過去の食事・購入のスナップショットを保持する。同一項目の競合は期待版で検出する。
- 生活イベントの訂正を解決するときは、一つの元IDだけでなく競合中の全先端IDを対象として保存する。別端末で同じ回を完了した場合は運動回IDでまとめる。同じ買い物リストの「今回購入」はテンプレートIDと別の購入回IDを持ち、再表示と二重タップでも同じ購入回IDを使う。
- 既存報酬は日付・習慣IDの単位を守り、旧習慣完了と新運動実績が同じ達成に対応するときは一回だけ集計する。新プランに移行した習慣の表示は既存印と新実績を突き合わせ、古い記録に新しい種目の回数を補完しない。新たな食事報酬は初版に加えない。
- サーバーで通知とiCalを作る際も、クライアントと同じ時刻・同じ生活revisionなら運動枠が一致すること。必要な情報は所要時間、対象の習慣・運動回、完了・見送り・本人固定などの配置用データに限定する。食材・実績の詳細を公開フィードに載せない。生活データを読めなかった場合、空と仮定して予定を配信し直さない。

## 具体例

1. **オフライン購入**：端末Aが卵2個購入を `id=P1` で保存。通信復帰時にP1を送信し、応答前に再送されても一意制約で1回だけ在庫+2。端末Bで別に卵1個を購入 `P2` した場合は+1も加わり、合計+3。
2. **実食後の材料訂正**：レシピ標準で卵1個を消費する食事 `M1` を記録し、翌日「実際は2個」と訂正 `C1 supersedes=M1`。投影はM1の1個を2個に置き換え、追加差分+1だけ減らす。C1再送でも合計消費は2個。
3. **食事・欠食の同時記録**：端末Aが昼食を食べた `M2`、端末Bが同じ枠を欠食 `M3` としてオフライン保存。同期後は要確認になり、在庫消費を二重に確定しない。本人が実食を選ぶと選択イベントがM2を有効化し、M3は競合履歴として残る。
4. **外食と未入力**：夕食の外食 `M4` は家の在庫を消費しない。何も操作しない夕食枠は `unknown` のままで欠食・外食に数えない。
5. **運動の再送**：完了ボタンの押下で `E1` を端末キューへ作り、応答が失われても同じE1を再送する。運動回数・報酬はE1一つから一度だけ算出。予定を延期しただけならE1は作られず、回数も増えない。
6. **旧端末からの保存**：新版が生活イベントを追加した後に、未更新端末が古い全体JSONを送る。旧端末のタスク編集は既存の app_state に保存できる。独立表の生活イベントと新版の在庫・実績は保持される。

## 受け入れ条件

- オフライン中の購入・実食・欠食・運動・訂正を端末再起動後も保持し、同期成功前にキューから消さない。
- 同一イベントIDを同じ内容で1回または複数回送っても、在庫・食事回数・運動回数・報酬への影響は一回分。
- 購入一括確定、材料消費訂正、実食から欠食への訂正は全件成功か全件失敗。部分保存状態を作らない。
- 自宅実食だけがレシピ量の在庫を消費し、外食・宅配・欠食・未入力は在庫を消費しない。
- 材料訂正・取消後の在庫は訂正後の総量を反映し、元レシピを変更せず差分だけ反映する。
- 同じ食事枠の実食対欠食、異レシピ実食、二重訂正は勝手に上書きせず要確認になる。競合解決後も元イベントと解決イベントを監査できる。
- 別端末で別食事枠を記録したものは両方残る。別々に購入した同じ品も両方加算される。
- 旧 `mealsAtHome` / `habitSkips` / `habitLogs` から推測した新しい購入・実食・運動イベントが生成されない。既存履歴は保持される。
- 未対応の生活イベント形式への書込みは拒否または保留する。旧端末の既存機能の保存は継続する。
- RPCのrevision不一致時は最新状態を取り直し、再マージして再送できる。保存失敗・通信中断でもイベントIDを変えない。
- SupabaseのRLSで別ユーザーのイベントを読めず、書けない。イベントなしの既存ユーザーと既存 `app_state` 行は移行後も読み込める。
